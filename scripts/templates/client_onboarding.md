## Running Your First Scan

```bash
# Pull and triage the latest alerts
python scripts/run_client.py --client-id $client_id

# Dry-run (analyse alerts but don't write back to SIEM)
python scripts/run_client.py --client-id $client_id --dry-run

# Limit to the 10 most recent alerts
python scripts/run_client.py --client-id $client_id --limit 10
```

## Recording Analyst Feedback

Feedback teaches the AI which alert types produce false positives in
**your** environment. The more feedback you record, the more accurate
the system becomes.

**Option A — Dashboard** (recommended)
Open `http://localhost:5000/feedback` and use the web form.

**Option B — Script**
```bash
python scripts/run_client.py --client-id $client_id --feedback
```

**Option C — API** (for SOAR integrations)
```
POST /api/feedback
{
  "rule_name": "brute_force_ssh",
  "analyst_verdict": "false_positive",
  "ai_correct": false,
  "notes": "Source is our Nessus scanner"
}
```

## Setting API Keys

AlertTriage never stores API secrets in YAML files. Set them as
environment variables before running:

```bash
# Anthropic (Claude models)
export ANTHROPIC_API_KEY=sk-ant-...

# OpenAI (GPT models, if used as fallback)
export OPENAI_API_KEY=sk-...

# SIEM token (replace CLIENT_ID_UPPER with your client ID in uppercase)
export ALERTTRIAGE_${CLIENT_ID_UPPER}_API_KEY=your-siem-token
```

## Troubleshooting

| Symptom | Fix |
|---|---|
| `API key not found` | Check env vars above |
| `SIEM connection refused` | Verify host/port and firewall rules |
| `No alerts returned` | Check SIEM index and time range |
| High false positive rate | Add environment context, record more feedback |
| Dashboard shows no data | Run a scan first, then record feedback |
